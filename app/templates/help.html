Help & Guide

How the orchestrator works, how your backups are stored, and how to recover in an incident.

What this tool does

The orchestrator copies your S3 buckets (or local folders) to a destination bucket, keeping a current mirror plus differential archives. Any historical point in time is restorable independently, so you can go back to exactly how your data looked on a given date. Backups run on a schedule you define (or manually on demand), are logged and audited, and old snapshots are pruned automatically so storage doesn't grow forever.

Why you'd use it

  • ✓ Simple, scheduled backups with a web UI — no cron scripts.
  • ✓ Point-in-time recovery: restore a single file or a whole day.
  • ✓ Automatic retention keeps storage under control.
  • ✓ Full audit trail of every action and every background run.
  • ✓ Works with any S3-compatible store: Garage, MinIO, AWS S3, R2, B2…

All transfers are performed by rclone, a battle-tested tool for copying data to/from cloud storage. It compares each file by checksum and size, so it only transfers what actually changed. Two rclone commands are used, and they behave very differently:

rclone copy

one-way copy · never deletes

  • • Copies new or changed files to the destination.
  • • Never deletes anything already at the destination.
  • • Overwrites a file only if the source changed.
Used for: restoring individual files/folders — safe, additive, non-destructive.

rclone sync

mirror · deletes extras

  • • Copies new or changed files to the destination.
  • • Deletes destination files that no longer exist in the source.
  • • Makes the destination an exact mirror of the source.
Used for: differential backups — syncs the source into the latest/ mirror and, via --backup-dir, moves every changed/deleted file into a timestamped archive/<ts>/ delta.

The exact rclone flags the orchestrator uses

Backup (differential, per run)
rclone sync \
  src:bucket \→ dest:bucket/latest/ \
  --backup-dir dest:bucket/archive/2026-08-21_12-00-00/ \
  --config /tmp/rclone.conf --checksum --transfers 4 \
  --no-update-modtime --stats 10s --stats-one-line
Restore latest / historical
# latest state (single copy)
rclone copy dest:bucket/latest/ \→ target:bucket/
# historical PITR to T: baseline, then every archive delta AT/after T, newest first
rclone copy dest:bucket/latest/ \→ target:bucket/
rclone copy dest:bucket/archive/2026-08-22_07-40-45/ \→ target:bucket/   # Step B 1/N (newest)
rclone copy dest:bucket/archive/2026-08-21_09-00-00/ \→ target:bucket/   # Step B N/N (…)

--checksum skips files whose content matches · --transfers 4 copies up to 4 files in parallel · --no-update-modtime avoids pointless re-copies · --stats 10s feeds the live progress bar.

The backup strategy

Every job keeps a current-state mirror in latest/. Each run syncs the source into it and uses --backup-dir to move any overwritten or deleted file into a timestamped archive/YYYY-MM-DD_HH-MM-SS/ delta. So the archive stores only changes — storage grows with what actually changed, not with full copies. A point-in-time restore reconstructs any state by overlaying the deltas taken at or after the target timestamp, newest first (the target run's own delta is applied too, reverting that run's changes). Retention keeps only the most recent RETAIN_DAYS deltas (the latest/ baseline is never pruned).

Snapshot isolation

If one day's data is wrong (bad deploy, accidental deletion, corruption), only that day's folder is affected — older snapshots remain untouched. You restore from the last good date.

Ransomware / accidental deletion
Restore from an archive taken before the incident.
Bad release / bad data
Point-in-time restore to yesterday's snapshot.
Full bucket loss
Restore-all into a fresh bucket; nothing is deleted (copy fallback).

How archives are stored

Structure on the destination bucket:
dest_bucket/
├── latest/                    ← current state (sync target, never pruned)
│   └── my-app/
│       ├── docs/report.pdf
│       └── config.yaml
└── archive/                   ← deltas of changed/deleted files
    ├── 2026-08-19_03-00-00/
    │   └── my-app/config.yaml     (old version moved aside)
    ├── 2026-08-20_12-00-00/
    │   └── my-app/…               (delta only)
    └── 2026-08-21_06-00-00/
        └── my-app/…               (delta only)

Each run syncs into latest/ and moves overwritten/deleted files into a timestamped archive/<ts>/ delta via --backup-dir — storage grows with changes, not full copies. Even a 3-hour schedule never collides.

How retention works

Every day at 03:00 UTC the orchestrator deletes archive folders older than RETAIN_DAYS (default {{ retain_days }}). Drag the slider to preview which dates would be kept:

Storage usage & housekeeping

  • • Storage grows roughly as RETAIN_DAYS × daily-source-size. Tune RETAIN_DAYS in Settings.
  • • Because the archive stores only changed/deleted bytes (deltas), storage grows with change rate, not with a full copy per run.
  • • Run logs are pruned daily (LOG_RETAIN_DAYS), and the orchestrator can back itself up to a bucket (SELF_BACKUP_DEST).

1 · Recover lost or damaged files

  1. Open Restore in the nav.
  2. Pick the source remote + bucket where the archive lives.
  3. Choose the date from the last good snapshot.
  4. Browse the tree and tick the files/folders you need.
  5. Choose a target remote/bucket and Restore selected (copy — nothing at the target is deleted).

2 · Recover a whole bucket

  1. Create the destination bucket (or reuse an empty one).
  2. Open Restore, pick the archive remote/bucket and the date.
  3. Choose Restore entire archive and the target bucket.
  4. Restore-all copies the state back with rclone copy — nothing at the target is ever deleted (non-destructive).

3 · Recover the orchestrator itself

If the orchestrator's container/database is lost, restore its metadata from the self-backup (if SELF_BACKUP_DEST is set) or from your own backup of the data directory:

  1. Restore orchestrator.db and .encryption_key into ./data/ — the key decrypts your remote credentials.
  2. Start the container. It re-reads the DB, marks crashed runs as failed, and rebuilds the scheduler.
  3. The backups themselves live on the buckets, independent of this app — deleting the orchestrator never deletes your backups.

Best practices

  • • Follow 3-2-1: at least 3 copies, 2 different media, 1 off-site. Use this tool for the off-site leg.
  • • Enable bucket versioning / object lock on the archive bucket to survive accidental retention purges.
  • • Back up data/ (or use SELF_BACKUP_DEST) so the orchestrator itself can be rebuilt.
  • • Test restores regularly — a backup you've never restored is just a hope.
